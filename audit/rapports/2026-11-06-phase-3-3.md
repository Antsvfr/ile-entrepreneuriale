# Phase 3.3 — Missions, exécution et communication (6 novembre 2026)

Moteur retenu par le président : **lancement manuel** (aucune exécution autonome). Tout est un événement du registre
chaîné ; aucune nouvelle base de données.

## Fonctionnalités réellement opérationnelles
| Fonction | Règle appliquée (contrôlée sous le verrou du journal) | Commande |
|---|---|---|
| Créer une mission | existant (`mission proposer`), planification par le DG, réservations présidentielles inchangées | `ile.py mission proposer`, `mission statut` |
| Attribuer à un agent, avec échéance et priorité | par un supérieur de l'agent ayant la permission, dans la même entreprise ; mission retenue (planifiée) | `ile.py org attribuer` |
| Démarrer | seul l'attributaire, pendant son exécution vérifiée (`--run`) | `org demarrer` |
| Transmettre un livrable | seul l'attributaire ; document de l'île gelé par son empreinte ; mission → vérification | `org livrer` |
| Valider / demander une correction | supérieur de l'attributaire (ou DG, ou président signé) ; jamais l'agent lui-même ; refus si le livrable a changé depuis sa transmission ; correction motivée → retour en cours | `org valider`, `org corriger` |
| Remonter un problème ou une décision | vers le supérieur ; peut bloquer la mission | `org remonter --bloquer` |
| Messagerie interne historisée | d'une identité vérifiée (ou DG / président) vers un agent, un poste ou un département | `org message` |
| Réunions | ouverte par une identité vérifiée ou le DG, close par l'organisateur, compte rendu au registre | `org reunion`, `org clore-reunion` |
| Statuts nouveaux, dérivés | `en_attente_validation` (livrable transmis), `bloque` (mission bloquée), `en_reunion` (réunion ouverte **et** exécution réelle) | `org agent <id>` |
| Historique et performance | missions de l'agent, missions terminées, corrections, livraisons dans les délais : **comptages d'événements**, jamais estimés | `org agent <id>` |
| Archivage | une mission validée passe en `terminee` et reste consultable | — |

## Exécution effective (test 8)
Sur une **copie** de l'île (journal temporaire) : mission attribuée à l'agent Architecte ; le Maire le lance et inscrit le
début de son exécution (déclaré, R-0006 — les hooks ne sont pas actifs dans la session de travail) ; **l'agent réel**
retrouve sa preuve d'exécution, démarre la mission, lit l'état des lieux de REV-EM, écrit une note fidèle (et signale
lui-même que le titre de la mission ne correspond pas au contenu du fichier), la transmet et prévient son supérieur —
4 événements vérifiés par son exécution (`[run]`) ; fin d'exécution ; validation par le DG ; mission terminée ; journal
intègre (92 événements). Traces : `audit/preuves-brutes/2026-11-06-phase-3-3/`.
Un lancement par une session Claude Code autonome (`claude -p`) a été **refusé par le système de sécurité** de
l'environnement (création d'agent autonome) : conforme au choix du lancement manuel ; non contourné.

## Tests
86/86 (Python 3.13 et 3.9), dont 7 nouveaux (`tests/test_travail.py`) : cycle complet avec correction, permissions
(expert, autre entreprise, identité déclarée, auto-validation, livrable hors de l'île), livrable modifié après
transmission, remontée et blocage, messages, réunion sans fausse présence, validation présidentielle signée.

## Limites
- La validation dans l'essai réel a été faite par le DG (aucun directeur n'avait d'exécution ouverte) ; un directeur
  lancé manuellement peut le faire sous sa propre identité vérifiée (testé).
- Hors d'une session dont les hooks sont actifs, le début d'exécution est déclaré par le Maire (visible comme tel).
- Le dépôt est public : missions et messages internes y sont lisibles.
- Pas encore d'interface : tout passe par la ligne de commande et l'API (phase 3.4).
