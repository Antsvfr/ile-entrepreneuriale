## 1. Audit préalable (avant construction)
- **Source de vérité unique** : le journal chaîné `orchestrateur/registre/journal.jsonl`. L'organisation est une
  projection calculée (`orchestrateur/organisation.py`, `projeter()`), exposée en local par `/api/organisation` et
  figée en ligne dans l'instantané `residence/instantane/organisation.json` (`./ile publier`). La phase 3.4 n'ajoute
  **aucune donnée** : l'interface lit cette projection et rien d'autre.
- **État réel du registre officiel** : 11 organisations reliées à un bâtiment (Résidence, Mairie, Conseil, Forge et
  7 maisons), 13 agents, 13 postes, **0 département, 0 équipe, 0 mission attribuée, 0 réunion, 0 message**, 9 missions
  proposées non attribuées. 6 bâtiments sont des chantiers sans entreprise.
- Conséquence assumée : en ligne, les bureaux affichent ces états vides **tels quels** (« aucun département enregistré »,
  « aucune réunion »…). Il est interdit de créer une fausse activité ; les vues pleines ont été démontrées sur une
  **fixture** (registre temporaire rempli par les vraies fonctions de l'île, jamais publié).

## 2. Architecture de la phase 3.4
```
Métropole 3D (index.html + ville.js)
  └─ clic sur un bâtiment relié → « Entrer dans l'entreprise » → entreprise.html#/e/<id>
entreprise.html + entreprise.js  (application d'une page, routeur sur le fragment #, consultation seule)
  ├─ source.js : local → /api/organisation ; publié → residence/instantane/organisation.json
  ├─ #/                      liste des entreprises
  ├─ #/e/<id>                accueil : direction, effectif réel, missions, situation dérivée, salles
  ├─ #/e/<id>/direction      bureau du directeur : profil, organigramme sous lui, missions suivies, messages,
  │                          livrables de son équipe, validations faites, historique
  ├─ #/e/<id>/organigramme   organigramme interactif (zoom, déplacement, repli, recherche, incohérences signalées)
  ├─ #/e/<id>/departements, /departement/<dep>, /equipes, /equipe/<poste>
  ├─ #/e/<id>/missions (filtres par statut), /reunions (réunions réelles seulement), /annuaire
  ├─ #/agent/<id>            profil : identité, statut + preuve + dernier événement, compétences, permissions,
  │                          activité comptée, hiérarchie navigable, missions, livrables, messages, réunions,
  │                          historique, graine visuelle stable (avatar : aucun, phase 4)
  └─ #/mission/<id>          fiche de mission
```
- Fil d'Ariane : Métropole → Entreprise → Département/Équipe → Agent → Mission.
- **Équipe** = un poste et les postes de la **même entreprise** placés directement sous lui (au registre). Les postes
  d'autres entreprises rattachés à un responsable (ex. les directeurs sous le Maire) sont signalés à part, hors équipe.
- **Statut** : repris tel quel de la projection (`_statut()` : suspendu, en réunion = réunion ouverte **et** exécution
  réelle, en exécution, en attente de validation, bloqué, disponible, hors ligne), avec sa preuve.
- **Incohérences** (cycles, supérieur inconnu, département inconnu, poste non pourvu, direction collégiale) : affichées,
  jamais corrigées en silence.
- **Phase 4 préparée sans visuel** : identifiant stable de l'agent et `apparence.graine` ; monogramme provisoire.
- **Sécurité** : toute donnée passe par `esc()` ; clés lues sans héritage de prototype ; aucun formulaire, aucune
  requête autre que GET ; CSP de `entreprise.html` **sans `'unsafe-inline'`** pour les scripts (script externe).
- **Données publiques** : `docs/architecture/DONNEES-PUBLIQUES.md` (tout le registre est public ; aucune fausse
  confidentialité ; fonctionnalités confidentielles bloquées tant qu'aucune architecture privée n'est décidée). Un
  bandeau le rappelle sur chaque vue en version publiée.

## 4. Fonctionnalités
**Opérationnelles (en ligne et en local)** : entrée depuis la métropole avec transition ; accueil de chaque entreprise ;
bureau du directeur ; départements, équipes, salle de réunion, annuaire, missions filtrables, fiche de mission ;
organigramme interactif ; profils complets et navigation hiérarchique ; recherche d'agent ; fil d'Ariane ; mobile ;
liens profonds rechargeables (fragment #) et navigateur neuf.

**Partielles** :
- en ligne, les données sont **figées à la date de l'instantané** (régénéré par `./ile publier`) ; aucun temps réel ;
- départements, équipes, réunions, livrables, messages : mécanismes et vues prêts et testés sur fixture, mais **vides
  au registre officiel** — rien n'est inventé pour les remplir ;
- identité visuelle : monogramme provisoire (avatars en phase 4).

**Impossibles sur GitHub Pages (non simulées)** : toute action (attribuer, valider, envoyer un message, ouvrir une
réunion) ; tout statut en direct ; toute donnée confidentielle. Les actions restent en ligne de commande locale
(`ile.py org …`) avec les contrôles d'autorisation existants ; l'interface ne propose aucun bouton d'action.

## 8. Risques et suites
- **Tout est public** (décision présidentielle) : missions, messages et réunions futurs seront lisibles par tous.
- L'instantané en ligne vieillit tant que `./ile publier` n'est pas relancé ; la date est affichée sur chaque page.
- Les bureaux en ligne resteront sobres tant que l'organisation réelle (départements, équipes, missions attribuées)
  n'est pas inscrite au registre par les commandes de la phase 3.3 ; c'est l'étape suivante logique, à décider par le
  président (aucune donnée n'a été ajoutée par cette mission).
- La performance 3D sur un ordinateur réel n'a pas été mesurée (environnement sans GPU) ; le diagnostic
  `?diagnostic=1` reste disponible.
- CSP : les autres pages (accueil, Résidence, vérification, métropole) gardent `'unsafe-inline'` pour leurs scripts
  intégrés ; à resserrer de la même façon.
- Phase 4 (avatars) **non commencée**, en attente de la validation de la phase 3.4 par le président.
